Subject: [PATCH v3] Validate inherited CHECK constraints when enabling
 enforcement

ALTER TABLE ... ADD CONSTRAINT on a child can merge a local ENFORCED
CHECK constraint into an inherited NOT ENFORCED one.  The merge marked
the constraint enforced and validated, but the existing rows had never
been checked against it, so a table could end up with a valid
constraint that some of its rows violate.  ADD CONSTRAINT ... NOT VALID
was marked validated the same way.

MergeWithExistingConstraint() now sets convalidated from the new
constraint's initially_valid.  ATAddCheckNNConstraint() remembers when
the merge enables enforcement, queues the Phase 3 check on the named
relation, and marks the constraint enforced on its descendants, queueing
the same check there, without changing their inheritance counts.  The
checks of normal ADD CONSTRAINT recursion are kept: ONLY is rejected
when there are children, and permissions are checked on each
descendant.  A descendant whose constraint is already ENFORCED but NOT
VALID makes the command fail; it must be validated first, as on master.
With NOT VALID, nothing is marked validated, so such a descendant is
left as is and the command succeeds.

This is the REL_18_STABLE version.  That branch has no ALTER CONSTRAINT
[NOT] ENFORCED for CHECK constraints, so the descendant handling is
done inline instead of through the enforceability traversal.
