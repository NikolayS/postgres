>      |

> ALTER TABLE c1 ADD CONSTRAINT cc (...);

Thanks Chao.

Since then, 0b12a5a7435a (8356d8e4dba6 on REL_19_STABLE) [1] made
enforcing a parent over an ENFORCED NOT VALID child an error, instead of
validating the child implicitly. v3 is rebased on top of it and follows
the same rule, so your case now hits that commit's error:

ERROR: constraint "cc" conflicts with NOT VALID constraint on child table "c2"
HINT: You may need to use ALTER TABLE ... VALIDATE CONSTRAINT on table "c2" first.

After "alter table c2 validate constraint cc", the add on c1 succeeds
and c1 and c2 end up enforced and valid. The test for this case now
expects the error.

This also made the force_validation handling dead code: a descendant
that is enforced but not valid errors out before it is reached, and the
merged root already gets convalidated from initially_valid. v3 removes
it, and core regression and isolation tests still pass.

> My understanding is that enforcing_conoid is used to remember an
> inherited constraint that is about to become locally enforced through
> the merge. If so, would it make sense to also check
> conform->coninhcount > 0 here?

I think it's not needed. MergeWithExistingConstraint() merges at the
named relation only when the existing constraint is not local (and the
relation is not a partition), so it is purely inherited, and
coninhcount > 0. A local NOT ENFORCED constraint with the same name
gets "already exists". Below the top level, merging an enforced
constraint into a NOT ENFORCED one errors out. So enforcing_conoid is
used (newcons == NIL) only after a merge into a purely inherited
constraint. I left the code as is; happy to add the check if you
prefer it as documentation.

> When force_validation is true, I think skip_validation should
> necessarily be false. If that is an invariant of this function, would
> it be worth adding an assertion to make that explicit, such as:
>
> Assert(!force_validation || !skip_validation);

It held (callers passed initially_valid for one and skip_validation for
the other), but force_validation is gone in v3, so there is nothing
left to assert.

Changes in v3:
- rebased on master; test blocks merged with the ones from 0b12a5a7435a
- force_validation removed
- one test now expects the error for an ENFORCED NOT VALID descendant
- an add with not valid over an ENFORCED NOT VALID descendant now
  succeeds: the constraint on the named table stays NOT VALID and the
  descendant is unchanged (new test)
- commit message, with Backpatch-through: 18
- a separate version for REL_18_STABLE

The master file applies as-is to REL_19_STABLE. REL_18_STABLE has no
ALTER CONSTRAINT [NOT] ENFORCED for CHECK, so that version does the
descendant handling inline in ATAddCheckNNConstraint(), raising the
same error for an ENFORCED NOT VALID descendant. It uses the same tests
and expected output as master. AI prepared the REL_18 version; I
haven't manually reviewed that code yet.

Tested with assertions, core regression and isolation tests pass on
each:
- master at b6178c942ea7 with v3-0001
- REL_19_STABLE at 4b1abd678223 with v3-0001
- REL_18_STABLE at d6694976c88c with the -REL_18 file

On master and REL_18_STABLE, the new tests fail without the code
changes and pass with them.
